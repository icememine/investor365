## Purpose

A customer buys a few familiar products and knows what they ordered, what it costs and whether payment completed; an operator imports a supplier stock snapshot. Exclusions (E1): no tax, delivery, discount, login, real bank or currency conversion.

## Experience

Calm and trustworthy: the shopping journey (Shop tab) is separate from diagnostics (Test desk). Hashes and certificates live in the desk, never in checkout. Every status says what was charged and what happens to the held items.

## Journey

browse → bag → review → place order (reserves) → pay → receipt, or declined / unconfirmed with recovery. Operator: choose file → read the declared meaning → validate → see conflicts or availability changes → confirm whole snapshot.

## Domain

VND exact integers; cart lines qty 1–9, 1–3 lines, unique SKU; per SKU H on hand, R reserved, A = H − R, 0 ≤ R ≤ H; snapshot = physical unsold units including reserved; order captures priced lines and total; instruction identity = order id scoped to this shop; payment states ready/pending/confirmed/declined/unknown/cancelled.

## Behavior

reserve only if q ≤ A, in the same step as order creation; confirmed: (H,R)→(H−q,R−q); declined or pre-payment cancel: (H,R)→(H,R−q); unknown keeps the reservation and makes no new charge; same id + same intent continues, changed intent refuses; snapshot with H_new < R rejected whole; imports never touch reservations or captured prices.

## Environment

profile panel 0.4 (grants panel.show, file.export); host keeps the session in browser storage (reload restores; Clear session resets), moves file bytes, runs the payment simulator (accept / decline / accept-lost / inquiry-unavailable) with a ledger tests may read and the graph cannot; the graph asks for a charge or an inquiry through state.request and the host answers with payment_result / inquiry_result events.
